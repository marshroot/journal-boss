## Расписание (пункт 5 плана)
**Найденная ошибка (важная):** время пар хранится в UTC, но SQLite возвращает его без признака часового пояса, поэтому JSON уходил в браузер без `Z`, а браузер читал его как *локальное* время — все пары, чат и дедлайны показывались со сдвигом на часовой пояс пользователя (для Хельсинки — на 2–3 часа). Из-за этого же «текущая пара» могла определяться неверно у пользователя.
- Добавлен `UtcDateTimeConverter` (`Services/`): все `DateTime` пишутся как UTC с `Z` и читаются как UTC; подключён к MVC и SignalR.
- `GET /api/schedule/personal` и `GET /api/parent/{id}/schedule`: параметры `from`/`to` нормализуются в UTC (раньше обрезались до «дня сервера»). `to` теперь исключающая граница.
- Админ: `PUT /api/admin/academic/schedule/{id}` (редактирование, проверка конфликтов группы/преподавателя без учёта самой пары, преподаватель всегда берётся из предмета, завершённую пару менять нельзя).
- Админ: удаление пары, у которой есть оценки, ДЗ или материалы, требует подтверждения (`?force=true`), иначе 409 — удаление каскадно сносит эти данные.
- Аудит: `schedule.create/update/delete`.
- UI `AdminAcademicPage`: пары сгруппированы по дням, кнопки «Изменить» и «Удалить», при выборе предмета преподаватель подставляется автоматически, подсказка про часовой пояс.

Уже было и проверено: у предмета обязателен преподаватель; система определяет текущую пару (`StartAt <= now <= EndAt`) для преподавателя и студента; студент и преподаватель видят своё расписание (`/api/schedule/personal`), родитель — расписание ребёнка.
**Не сделано:** недельный календарь-сетка (сейчас списком по дням), копирование недели, отдельный выбор аудитории с проверкой занятости.

## Файлы ДЗ и материалов (пункт 7 — реализовано)

На следующем шаге закрыта недоделка из раздела ограничений: файлы теперь можно привязывать непосредственно к учебному материалу и домашнему заданию, а не только к паре.

### Backend

Добавлены сущности:
- `MaterialAttachment` → `StudyMaterial`;
- `HomeworkAttachment` → `LocalHomework`.

Для существующей SQLite-базы новые таблицы создаются через `SqliteSchemaUpgrades` из EF-модели без удаления существующих данных.

Новые API:

```text
GET    /api/attachments/material/{materialId}
POST   /api/attachments/material/{materialId}
GET    /api/attachments/material/{materialId}/{id}/download
DELETE /api/attachments/material/{materialId}/{id}

GET    /api/attachments/homework/{homeworkId}
POST   /api/attachments/homework/{homeworkId}
GET    /api/attachments/homework/{homeworkId}/{id}/download
DELETE /api/attachments/homework/{homeworkId}/{id}
```

Правила доступа:
- преподаватель может загружать/удалять файлы только у своих материалов и ДЗ;
- администратор имеет полный доступ;
- студент видит файлы только материалов, опубликованных для его группы, и ДЗ своей группы;
- родитель видит файлы материалов/ДЗ группы связанного ребёнка;
- черновик материала не раскрывает свои вложения студентам и родителям;
- скачивание проходит через авторизованный API, поэтому storage не публикуется напрямую;
- путь к файлу проверяется после `GetFullPath`, чтобы исключить path traversal.

Ограничения загрузки те же, что у существующих вложений пары:
- максимум 25 MB;
- PDF, TXT, Markdown, PNG/JPEG/WebP, ZIP, DOCX, PPTX, XLSX;
- расширение должно соответствовать заявленному Content-Type;
- имя файла очищается от недопустимых символов;
- фактический storage key генерируется сервером через GUID.

### Frontend

`MaterialsPage`:
- преподаватель/администратор может добавить файл к выбранному материалу;
- можно скачать или удалить вложение;

- преподаватель может загрузить, скачать и удалить файл;

`LocalHomeworkPage`:
- студент и родитель видят вложения задания;
- скачивание выполняется через авторизованный `fetch`, а не прямой URL.

### Аудит

Добавлены действия:
- `attachment.material.upload`
- `attachment.material.delete`
- `attachment.homework.upload`
- `attachment.homework.delete`
- существующее `attachment.download` используется и для новых типов вложений.

### Что проверить вручную

1. Преподаватель создаёт материал и загружает PDF.
2. Пока материал — черновик, студент не должен видеть файл.
3. После публикации студент открывает материал и скачивает PDF.
4. Преподаватель удаляет файл — скачивание после удаления должно вернуть `404`.
5. Преподаватель создаёт ДЗ и загружает DOCX/ZIP.
6. Студент открывает `/homework` и видит файл задания.
7. Родитель открывает ДЗ выбранного ребёнка и также видит файл.
8. Попытка обратиться к файлу другого материала/ДЗ должна возвращать `403` или `404` в зависимости от того, существует ли сам ресурс.
9. Файл >25 MB, неизвестный MIME или несовпадающее расширение должны отклоняться.
10. После перезапуска Docker файлы должны сохраняться в volume `journal_uploads`.

## P9 — совместный Code Lab (Yjs + Hocuspocus)

Добавлен self-hosted realtime-контур для совместного редактирования кода. В существующий Monaco Editor добавлена синхронизация содержимого через Yjs, а Hocuspocus используется как WebSocket/CRDT-сервер. Hocuspocus сохраняет документы в отдельной SQLite-базе, поэтому существующая учебная БД не переписывается. Hocuspocus 4.x официально поддерживает Yjs и SQLite persistence.

Безопасность: ASP.NET Core выдаёт отдельный короткоживущий JWT только после проверки доступа пользователя к конкретному `CodeExercise`. Токен содержит `collab_room`; Hocuspocus проверяет подпись JWT, issuer, audience, срок действия и точное совпадение комнаты. Поэтому знание ID другой задачи само по себе не даёт доступа к её документу.

Docker добавляет сервис `collab` на `1234/tcp` и volume `collab_data`. Для локального браузера используется `VITE_COLLAB_URL=ws://localhost:1234`.

### Проверка P9

1. Запустить `docker compose up --build`.
2. Открыть Code Lab с задачей у студента.
3. Убедиться, что статус редактора становится `Онлайн`.
4. Открыть ту же задачу во втором браузере под пользователем с доступом.
5. Ввести текст в одном окне и проверить его появление во втором.
6. Перезапустить `collab` и проверить, что содержимое восстановилось из `collab_data`.
7. Проверить, что пользователь без доступа к задаче получает отказ при выдаче collaboration token.

Пока не включено: курсоры/awareness с именами участников и совместная Excalidraw-доска. Это отдельные следующие шаги.


## P10 — совместная доска Excalidraw + production WebSocket routing

Доска `/lesson-board?lessonId=...` теперь использует тот же Hocuspocus/Yjs-контур, что и Code Lab.

### Реализовано
- Новый `POST /api/collaboration/lesson/{lessonId}/board-token`.
- Сервер выдаёт collaboration JWT только администратору, преподавателю-владельцу пары или студенту своей группы.
- Для каждой пары отдельная комната `lesson-board-{lessonId}`; Hocuspocus принимает документ только при точном совпадении `collab_room`.
- Excalidraw элементы хранятся в Y.Array и автоматически синхронизируются между браузерами.
- Состояние доски сохраняется в SQLite Hocuspocus (`collab_data`), поэтому перезапуск `collab` не удаляет рисунок.
- Добавлена awareness-информация с именами участников; на доске отображается список подключённых пользователей.
- Code Lab также показывает число/имена участников через Yjs awareness.
- В production браузер больше не обязан обращаться к `ws://localhost:1234`: nginx проксирует `/collab` в сервис `collab`.
- В development Vite проксирует `/collab` на локальный Hocuspocus.
- `frontend` теперь ждёт `backend` и `collab` healthcheck перед стартом.

### Проверка P10
1. `docker compose up --build`.
2. Открыть одну пару в двух браузерах двумя пользователями, имеющими доступ.
3. Открыть `/lesson-board?lessonId=<id>`.
4. Нарисовать фигуру/стрелку в первом браузере — изменения должны появиться во втором.
5. Проверить список участников.
6. Перезапустить `collab` (`docker compose restart collab`) и снова открыть доску — элементы должны восстановиться.
7. Открыть ту же URL пользователем другой группы — выдача board token должна вернуть `403`.
8. Проверить Code Lab: список участников должен отображать подключённых пользователей.

## P11 — секреты legacy-модуля

Убран hard-coded `APPLICATION_KEY` из `JournalBackend` и встроенного C#-бота. Теперь значение берётся только из переменной окружения `APPLICATION_KEY`; в `.env.example` добавлена пустая настройка. ## Итог текущей итерации

Текущая ветка содержит P1–P11 из этого документа. Критические Docker-проблемы, выявленные при ручном запуске, устранены: backend healthcheck использует `curl`, frontend ходит к API через same-origin nginx, realtime `/hubs` проксируется, а Hocuspocus `/collab` также проходит через frontend. Добавлены совместная Excalidraw-доска и awareness участников.

Фактический `dotnet build` и полный `docker compose up --build` в этой среде не подтверждены: SDK Docker/.NET здесь недоступны, а установка frontend-зависимостей по сети не завершилась. Поэтому эти проверки остаются обязательными на машине разработки.
